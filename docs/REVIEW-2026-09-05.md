# FlowPilot Technical Review — 2026-09-05

Scope: static source/config review plus local `testDebugUnitTest` and `assembleDebug` verification.

Status: 47 JVM unit-test files discovered. `testDebugUnitTest` passed. Debug APK built successfully at `app/build/outputs/apk/debug/app-debug.apk` (20,211,031 bytes). No device smoke test or release APK test ran.

## Critical

### Engine restart race can duplicate automation execution and leak listeners

**Evidence**

- `app/src/main/java/com/flowpilot/app/engine/AutomationService.kt:35-40`
- `app/src/main/java/com/flowpilot/app/engine/AutomationService.kt:45-51`
- `app/src/main/java/com/flowpilot/app/engine/AutomationEngine.kt:56-69`
- `app/src/main/java/com/flowpilot/app/engine/AutomationEngine.kt:100-114`

`AutomationService` checks/replaces `engine` without synchronization. Concurrent service starts can construct multiple `AutomationEngine` instances. Each registers trackers/listeners; only latest instance remains referenced and is stopped later.

**Impact:** duplicate rule runs, leaked receivers/sensors/callbacks until process death, extra battery drain.

**Fix:** serialize service start/stop on main thread or a mutex. Keep one engine instance. Stop and join an old instance before replacement. Add concurrency test for repeated start commands.

### Imported rules can become privileged automations without per-rule safety review

**Evidence**

- `app/src/main/java/com/flowpilot/app/data/backup/BackupManager.kt:61-89`
- Import UI/repository flow should be reviewed together with rule enable-state handling.

Imports accept externally supplied JSON rules. These rules may contain actions such as webhook calls, SMS sending, calls, app launches, or Shizuku-backed system actions.

**Impact:** importing a shared automation can activate high-impact actions without a clear per-rule risk review.

**Fix:** import all rules disabled by default. Display an action/permission summary and require explicit enablement after import. Treat imported secrets and URLs as untrusted input.

## High

### Every rule execution requests location, even when no action needs it

**Evidence**

- `app/src/main/java/com/flowpilot/app/engine/AutomationEngine.kt:420-438`
- `app/src/main/java/com/flowpilot/app/engine/LocationFetcher.kt:32-94`

`executeAll()` unconditionally calls `LocationFetcher.getCoordinates()`. A rule that only toggles a setting, shows a notification, or changes audio can initiate a location request and wait up to five seconds.

**Impact:** unnecessary location access, battery cost, Android foreground-service/policy complexity, surprising privacy behavior.

**Fix:** inspect selected actions/templates first. Fetch coordinates only when an action actually references `${location.*}` or needs location.

### Location fallback can send stale coordinates

**Evidence**

- `app/src/main/java/com/flowpilot/app/engine/LocationFetcher.kt:79-83`

After fresh location lookup times out, any cached location is returned with no maximum age or accuracy requirement.

**Impact:** webhook or emergency SMS can contain hours- or days-old coordinates.

**Fix:** set explicit fallback limits, for example maximum age and minimum accuracy. Return a clear unavailable state when no valid recent location exists.

### HTTP webhook permits plaintext sensitive-data transmission

**Evidence**

- `app/src/main/java/com/flowpilot/app/actions/WebhookExecutor.kt:127-130`
- `app/src/main/java/com/flowpilot/app/actions/WebhookTemplateRenderer.kt:63-69`

Webhook validation allows `http` as well as `https`. Templates can include SMS data, Wi-Fi SSID, location, and other user data.

**Impact:** credentials or sensitive template values may traverse unencrypted networks.

**Fix:** permit HTTPS by default. Require a separate, explicit risk acknowledgement for HTTP, or remove HTTP support.

### Export/share exposes decrypted webhook secrets in plaintext

**Evidence**

- `app/src/main/java/com/flowpilot/app/data/backup/BackupManager.kt:45-58`
- `app/src/main/java/com/flowpilot/app/ui/AppViewModel.kt:428-440`
- `app/src/main/java/com/flowpilot/app/ui/AppViewModel.kt:450-467`
- `app/src/main/java/com/flowpilot/app/data/model/Automation.kt:347-371`

Backup and single-rule export call `withDecryptedSecrets()`. Share sends plaintext content through both FileProvider and `Intent.EXTRA_TEXT`.

**Impact:** selected share targets receive API keys, bearer tokens, credential-bearing URLs, message templates, phone numbers, and configured payloads. Plaintext copies can remain under cache sharing files.

**Fix:** exclude secrets by default. If portable secret export is needed, require explicit confirmation and password-encrypt the archive. Avoid duplicating sensitive JSON in `Intent.EXTRA_TEXT`.

### Exported widget receiver accepts arbitrary toggle broadcasts

**Evidence**

- `app/src/main/AndroidManifest.xml:204-215`
- `app/src/main/java/com/flowpilot/app/widget/FlowPilotWidgetProvider.kt:100-112`

The widget receiver is exported and handles `com.flowpilot.app.widget.ACTION_TOGGLE_ENGINE` without caller validation.

**Impact:** another installed app can toggle the automation engine.

**Fix:** make the receiver non-exported if widget delivery still works, or protect custom action with a signature permission. Verify PendingIntent behavior after change.

### Android 14+ reboot/update service startup can silently fail

**Evidence**

- `app/src/main/java/com/flowpilot/app/engine/BootReceiver.kt:22-27`
- `app/src/main/java/com/flowpilot/app/engine/AutomationService.kt:82-96`
- `app/src/main/AndroidManifest.xml:49-50`
- `app/src/main/AndroidManifest.xml:125-134`

Boot receiver starts a foreground service from background. Service includes location type whenever coarse/fine permission exists; background location constraints are not checked. Service startup failures are broadly caught, leaving engine stopped.

**Impact:** rules may not restart after reboot/update on Android 14–16.

**Fix:** start special-use-only mode at boot when background location is unavailable. Defer active location work until allowed. Surface startup failure to user. Add real reboot/update tests on Android 14–16.

### Google Play restricted-permission publication risk

**Evidence**

- `app/src/main/AndroidManifest.xml:11-13` (`QUERY_ALL_PACKAGES`)
- `app/src/main/AndroidManifest.xml:67-69` (`RECEIVE_SMS`, `SEND_SMS`)
- `app/src/main/java/com/flowpilot/app/engine/SmsReceiver.kt:29-46`
- `app/src/main/java/com/flowpilot/app/actions/SmsExecutor.kt:82-95`

App requests broad package visibility and SMS receive/send capabilities. These are policy-sensitive on Google Play.

**Impact:** Play review rejection or required policy declarations/qualifying use cases.

**Fix:** remove permissions not essential to installed distribution flavor. If Play distribution is intended, document qualifying core use, complete declarations, evaluate role/default-SMS restrictions, and consider a separate non-Play flavor.

### Privacy documentation conflicts with user-configured outbound behavior

**Evidence**

- `README.md:33-38`
- `README.md:103-104`
- `README.md:202-208`
- `app/src/main/java/com/flowpilot/app/actions/WebhookTemplateRenderer.kt:63-69`
- `app/src/main/java/com/flowpilot/app/actions/SmsExecutor.kt:57-66`

README says rules and sensitive data never leave the phone, but configured webhook/SMS/export actions can deliberately transmit data.

**Impact:** misleading privacy claim and inadequate user disclosure.

**Fix:** say no analytics/cloud sync is used, but clearly disclose that user-configured webhook, SMS, and export/share actions send selected data to chosen destinations.

## Medium

### In-memory SMS and notification queues lose events on process death

**Evidence**

- `app/src/main/java/com/flowpilot/app/engine/SmsEventTracker.kt:20-21`
- `app/src/main/java/com/flowpilot/app/engine/FlowPilotNotificationListener.kt:127-132`

Pending events are held only in process memory.

**Impact:** SMS/notification triggers can disappear between receipt and engine processing if process dies or service startup is delayed.

**Fix:** persist minimal event metadata before processing, then remove on completion. If notification/SMS body persistence is necessary, encrypt and disclose it; otherwise document best-effort delivery.

### Release workflow can publish untested release APKs

**Evidence**

- `.github/workflows/ci.yml:31-35`
- `.github/workflows/release.yml:37-43`

CI runs debug unit tests and debug assembly. Release workflow builds signed APK without running tests first.

**Impact:** tag release can publish a broken/minified APK.

**Fix:** run `testDebugUnitTest`, `lintDebug`, and `assembleRelease` validation before signed publish. Add release smoke/device test where possible.

### CI does not validate release shrinking/minification ahead of release

**Evidence**

- `.github/workflows/ci.yml:31-35`
- `app/build.gradle.kts:34-40`

Release enables R8 and resource shrink, but regular CI does not assemble release.

**Impact:** R8/resource shrinker failures reach release stage.

**Fix:** add unsigned `assembleRelease` to CI.

### Release signing configuration fails late with missing secrets

**Evidence**

- `app/build.gradle.kts:23-29`
- `app/build.gradle.kts:41-44`
- `.github/workflows/release.yml:33-35`

Signing is configured when keystore file exists, without explicit validation that password, alias, and key password exist. Base64 keystore decode/output also lacks explicit validation.

**Impact:** unclear late Gradle/signing failures.

**Fix:** fail configuration early with a clear message when any signing input is absent. Validate `KEYSTORE_BASE64`, decode strictly, and verify non-empty keystore file.

### Manual release workflow can publish from an unintended ref

**Evidence**

- `.github/workflows/release.yml:4-7`
- `.github/workflows/release.yml:60-70`

`workflow_dispatch` can run outside a validated version-tag flow.

**Impact:** unintended release/tag publication.

**Fix:** restrict publishing to validated `v*` tags, or require an explicit validated tag input and refuse branch refs.

### GitHub Actions are pinned to mutable major tags

**Evidence**

- `.github/workflows/ci.yml:17,20,26,38`
- `.github/workflows/release.yml:19,22,28,61`

Third-party actions use mutable major tags rather than reviewed commit SHAs.

**Impact:** supply-chain/reproducibility risk, especially in release workflow with signing credentials.

**Fix:** pin actions to reviewed commit SHAs and update through Dependabot/Renovate.

### Foreground-service declaration and implementation scope need alignment

## Notes / positive controls

- `android:allowBackup="false"` is set in `AndroidManifest.xml:93`.
- FileProvider is restricted to `cache-path` `shares/` in `app/src/main/res/xml/file_paths.xml:2-4`.
- Webhook logging redacts sensitive headers and URL query values.
- SMS sender logging is masked; notification title/body is not persisted or logged.
- R8 serialization safety appears adequate with current direct generated serializer usage and kotlinx.serialization consumer rules. `proguard-rules.pro:14-17` comment is misleading, though: it only keeps `@Keep` members and is not what protects serialization models.

## Recommended remediation order

1. Serialize `AutomationService`/`AutomationEngine` lifecycle; prevent duplicate engines.
2. Fetch location only when required; enforce stale-location limits.
3. Make webhooks HTTPS-only by default.
4. Secure export/import: secret-free default export, encrypted opt-in secret export, disabled-by-default imported rules.
5. Protect widget toggle receiver.
6. Repair boot/Android 14+ foreground-service startup behavior.
7. Add release CI gates and harden signing/release workflow.
8. Resolve Play policy/disclosure scope before Play distribution.
9. Add device/instrumentation smoke coverage.
